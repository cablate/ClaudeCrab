# 開發工作流程

## 核心原則

**理解業務需求優先於技術實作**

寫程式之前，先確認「這段程式碼要解決什麼問題」。技術選型服務於業務需求，不是反過來。

**能簡單就簡單**

三行能解決的事不寫十行。不為假想的未來需求過度設計。當下的最小可用解法，勝過未來的完美架構。

**可交付 = 可運作 + 可理解 + 可維護**

程式碼不只是給機器跑的，也是給未來的自己或協作者讀的。

## 工作流程

### 1. 理解需求（先問，再動手）

收到需求時，先確認：
- **目標**：這個功能要達成什麼業務效果？
- **邊界**：哪些在範圍內、哪些不是？
- **限制**：有沒有技術限制或既有架構要遵守？
- **成功條件**：怎樣算做完了？

> 如果需求模糊，先列出假設請使用者確認，不要自己猜。

**範例：需求釐清**

| 模糊需求 | 正確做法 |
|---------|---------|
| 「幫我加個通知功能」 | 「通知要在什麼時機觸發？推送給誰？顯示在哪裡？」 |
| 「速度太慢，優化一下」 | 「哪個操作慢？慢多少算可接受？有沒有效能 baseline？」 |
| 「這個 bug 修一下」 | 「什麼步驟會觸發？預期行為是什麼？」 |

### 2. 方案設計（想清楚再寫）

實作前先思考：
- 有幾種做法？各自的取捨是什麼？
- 選哪個方案？為什麼？
- **影響範圍**：這次改動會影響哪些現有功能、哪些檔案？明確說出來再動手。

複雜功能要先討論方案，獲得確認後再動手。

### 3. 實作

- 遵循既有的程式碼風格和命名規範
- 每次改動範圍要小、要聚焦
- 邊做邊確認方向正確（不要悶頭做完再說）

### 4. 測試驗證

實作完成後，驗證功能正確：
- **基本路徑**：主要使用情境是否正常運作？
- **邊界條件**：空值、極端值、異常輸入有沒有處理？
- **回歸測試**：現有功能有沒有被破壞？
- 專案有自動化測試時，確認測試通過後再交付

> 寫程式 → 跑測試 → 修問題，這個循環越短越好。

### 5. 品質確認（交付前的自我審查）

參考 [code-quality.md](references/code-quality.md) 進行自我審查。

### 6. 交付

- 說明改了什麼、為什麼這樣改
- 如果有需要使用者確認的決策，明確提出
- **重要技術決策必須記錄**：放到對應的 proj-* skill 的 decisions/ 或 CLAUDE.md Lessons Learned
