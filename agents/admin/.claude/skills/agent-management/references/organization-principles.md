# 組織設計原則

這是 ClaudeCab 組織架構的核心設計原則。所有管理決策都應該以這些原則為依據。

---

## 四大目標

組織設計要滿足這四個目標：

### 1. 單一職責

每個員工有明確的職責邊界，不混雜。

- Coder 專注寫程式
- 秘書專注任務記錄
- Admin 專注 Agent 管理
- 不能「圖方便」把不合適的工作丟給不合適的人

**衍生規則**：
- 員工要能自主判斷「這不該我做」並轉介
- 知識記錄只記職責範圍內的東西
- 一個 Skill 解決一類問題，不做萬用容器

### 2. 可追蹤

管理者能掌握每個員工的狀態和成長。

- 知道誰做了什麼
- 知道誰學了什麼
- 知道誰的能力有什麼變化

**衍生規則**：
- 重要改動要記錄到 changelog
- 新建 Skill 要通知管理者
- 定期掃描員工的變更

### 3. 可複製

好的能力包可以分發給需要的人。

- 一個 Skill 設計好，可以給多個員工用
- 知識不該鎖在某個人的專屬容器裡
- 跨領域的知識做成獨立 Skill，誰需要就複製給誰

**衍生規則**：
- 避免「個人專屬」的知識容器（如 Wisdom 容器）
- 通用 Skill 放在 `_example/.claude/skills/`
- 獨立 Skill 用命名慣例（`knowledge-`、`method-`、`proj-`）

### 4. 持續演化

員工會越來越強，不是每次從零開始。

- 學到的東西不會隨 session 消失
- 經驗能累積成可複用的知識
- 組織整體的能力是累積的

**衍生規則**：
- 所有員工載入 `sys-self-evolution` 原則
- 知識就地歸屬（學到就更新對應 Skill）
- 沒有既有 Skill 就建新的

---

## 原則之間的優先級

當原則之間有衝突時，優先級為：

1. **單一職責** > 其他
   - 寧可多一個人處理，不要讓一個人做太多種事

2. **可追蹤** > 可複製、持續演化
   - 寧可記錄多一點，不要失去追蹤能力

3. **可複製** ≈ 持續演化
   - 這兩個通常不衝突，但如果衝突，以具體情況判斷

---

## 設計決策的檢驗

做任何管理決策時，用這些問題檢驗：

1. **這符合單一職責嗎？**
   - 這個設計會不會讓某人承擔太多種工作？
   - 這個 Skill 會不會承載太多種知識？

2. **這可追蹤嗎？**
   - 管理者能知道這個改動嗎？
   - 未來能追溯這個決策的脈絡嗎？

3. **這可複製嗎？**
   - 如果這個能力很好，能給其他人嗎？
   - 還是被鎖在某個人專屬的地方？

4. **這支持持續演化嗎？**
   - 員工學到的東西能保留嗎？
   - 還是會隨 session 消失？

## 員工規劃原則：孵化器模式

### 核心理念

**秘書是孵化器，成熟了才分出去。**

新的工作類型不是一開始就建立專職員工，而是：

1. **先給秘書試跑**：新任務、新流程先在秘書身上驗證
2. **跑通可重複的路**：確認流程可重複、協作模式成熟、效果滿意
3. **成熟後才分出去**：有足夠的經驗和確定性，再考慮建立專職員工

### 為什麼這樣做

- **降低試錯成本**：不確定的東西不急著建架構
- **累積實戰經驗**：在秘書身上跑出來的流程是經過驗證的
- **避免過早抽象**：等真正理解需求後再做分工

### 判斷「成熟」的標準

- 流程已經跑通，能穩定重複
- 協作模式已定型，不需要頻繁調整
- 使用者對效果滿意
- 分出去的 ROI 足夠高（維護成本 < 效益）

### 範例

| 能力 | 狀態 | 說明 |
|------|------|------|
| TurboScribe 轉錄 | 成熟 | 流程穩定，可以考慮分出去（但目前 ROI 不高，先留著） |
| 社群貼文優化 | 成熟中 | 框架建立了，但協作模式還在調整 |
| Coder 開發流程 | 成熟中 | 一個 Coder 包所有專案，未來成熟後可能一專案一員工 |

### 這解釋了什麼

秘書有很多 Skill 不是因為她「什麼都做」，而是因為很多能力還在孵化階段。這符合組織原則——在確定職責分工之前，先讓流程跑通。

## 反模式

### ❌ Wisdom 容器

把所有可複用經驗集中到一個專屬容器。

**問題**：邊界模糊、違反單一職責、無法複製

**正確做法**：知識就地歸屬，建立獨立 Skill

### ❌ 圖方便的任務分配

「反正這個人能做，就給他做」

**問題**：違反單一職責、長期會讓員工職責模糊

**正確做法**：找職責最匹配的人，沒有就先問

### ❌ 忘記記錄

改了設定但沒記錄到 changelog

**問題**：失去追蹤能力、未來無法理解決策脈絡

**正確做法**：每次改動當輪就記

### ❌ 把通用 Skill 放錯地方

放到 `_shared/` 或某個員工目錄

**問題**：新員工建立時不會自動帶入

**正確做法**：通用 Skill 放 `_example/.claude/skills/`

## 未來方向

這些原則會隨著組織發展持續調整。當發現：

- 某個原則不適用了
- 有新的原則需要加入
- 原則之間的優先級需要調整

應該更新這份文件，並記錄到 `.claude/skills/agent-management/references/agent-changes-log.md`。
