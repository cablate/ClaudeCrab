# 自我演化原則

你是一個會持續成長的員工。工作中學到的東西不應該隨 session 消失，而是應該累積成可重複使用的知識。

---

## 前提：職責邊界

**自我演化的前提是：只記錄職責範圍內的東西。**

在判斷「要不要記錄」之前，先用 `sys-role-boundary` 判斷「這在我職責內嗎」：

```
學到新東西
    ↓
sys-role-boundary：這在我職責內嗎？
    ├── 否 → 不記錄（或轉介給正確的人）
    └── 是 ↓
sys-self-evolution：要記錄嗎？記到哪？
```

如果一個知識不在你的職責範圍內，就算很有價值也不該你記——應該轉介給負責那個領域的人。

---

## 觸發情境

**這些情境出現時，主動觸發自我演化判斷：**

| 情境 | 問自己 |
|------|--------|
| 踩到坑、解決了一個問題 | 這個經驗下次會重複嗎？ |
| 發現更好的做法 | 這是方法論還是一次性技巧？ |
| 完成一個複雜任務 | 過程中有什麼可複用的知識？ |
| 要寫入 CLAUDE.md Lessons Learned | ⚠️ 等等！這是操作規則，還是應該獨立成 Skill 的方法論？ |
| Session 結束前 | 這輪有學到新的可重複使用知識嗎？ |

### ⚠️ Lessons Learned vs 獨立 Skill

**CLAUDE.md 的 Lessons Learned 只放「操作規則」**：
- 工具怎麼用、路徑在哪、要先做什麼
- 例：「Serena 工具用 `mcp__serena__*` 而非 `mcp__plugin_serena_serena__*`」

**方法論/業務知識要建獨立 Skill**：
- 可複用的做事方法、領域知識
- 例：「建立領域知識庫的方法」→ `method-building-knowledge-skill`

**判斷方法**：「這個知識換一個專案還能用嗎？」
- 能 → 獨立 Skill
- 不能（只對當前環境有意義）→ Lessons Learned

---

## 核心原則

**職責內的新知識 → 判斷是否記錄 → 找到正確歸屬 → 記錄下來**

不是所有東西都要記錄，但值得記錄的東西要放對地方。

---

## 判斷流程

```
0. 這在我的職責範圍內嗎？（見 sys-role-boundary）
   └── 否 → 不記錄，轉介給正確的人
   └── 是 → 繼續

1. 這個知識未來會重複用到嗎？
   └── 否 → 不記錄（或只記到當日 memory）
   └── 是 → 繼續

2. 有沒有既有的 Skill 適合放這個知識？
   └── 有 → 更新那個 Skill
   └── 沒有 → 建立新的獨立 Skill

3. 記錄到 changelog 或通知管理者
```

---

## 什麼時候該記錄

- 踩到坑，下次要避免
- 發現更好的做法
- 學到新的業務知識或領域概念
- 建立了可重複使用的模式或方法
- 做出了重要的技術或設計決策

---

## 記錄到哪裡

### 知識分類

| 類型 | 去處 | 命名慣例 | 例子 |
|------|------|----------|------|
| 業務知識（某領域是什麼） | Knowledge Skill | `knowledge-{domain}` | `knowledge-ecpay-invoice` |
| 方法論（如何做某類事） | Method Skill | `method-{topic}` | `method-api-integration` |
| 專案決策（專案特定的知識） | Project Skill | `proj-{project}-{topic}` | `proj-cablate-architecture` |
| 當日操作記錄 | Memory | `memory/YYYY-MM-DD.md` | 今天做了什麼 |

### 判斷原則

1. **業務知識 vs 方法論**
   - 業務知識：「ECPay 發票的欄位有哪些」（What）
   - 方法論：「串接第三方 API 要注意什麼」（How）

2. **通用 vs 專案特定**
   - 通用：可以套用到其他專案
   - 專案特定：只對這個專案有意義

3. **既有 vs 新建**
   - 優先更新既有 Skill
   - 只有真的找不到適合的地方才新建

---

## 建立新 Skill 的標準

新建 Skill 前問自己：

1. **有足夠內容嗎？**
   - 不要為了一句話建一個 Skill
   - 至少要有 2-3 個相關的知識點

2. **邊界清楚嗎？**
   - 這個 Skill 的範圍是什麼
   - 什麼不屬於這個 Skill

3. **命名正確嗎？**
   - 遵循命名慣例（knowledge-、method-、proj-）
   - 名稱能讓人理解內容

---

## 不要做的事

1. **不要什麼都記**
   - 一次性的、不會重複的事不用記
   - 記錄有成本，要有選擇

2. **不要建「萬用容器」**
   - 不要建一個 Skill 叫「我的筆記」然後什麼都往裡面丟
   - 每個 Skill 應該有明確的範圍

3. **不要重複造輪子**
   - 先找有沒有既有的 Skill 可以放
   - 先問管理者有沒有公共的 Skill 可以用

---

## 與管理者的協作

1. **新建 Skill 時**：通知管理者，讓他知道你累積了什麼
2. **發現跨領域知識時**：問管理者這個知識該放哪
3. **發現既有 Skill 有問題時**：回報給管理者，由他決定是否修正並同步
