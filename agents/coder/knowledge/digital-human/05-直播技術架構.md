# 直播技術架構詳解

## 推流協議比較

### 三大主流協議

| 協議 | 延遲 | 擴展性 | 適用場景 |
|------|------|--------|----------|
| **RTMP** | 3-5 秒 | 高 | 傳統直播、預錄播放 |
| **WebRTC** | < 500ms | 中等 | 即時互動、電商直播 |
| **HLS/DASH** | 10-30 秒 | 極高 | 大規模分發、回放 |

---

## RTMP 架構

### 傳統 RTMP 直播流程

```
┌─────────┐    RTMP     ┌─────────┐    HTTP-FLV    ┌─────────┐
│ 主播端   │ ─────────→ │  CDN    │ ────────────→  │  觀眾端  │
│ (OBS)   │    推流     │ 邊緣節點 │     拉流       │ (播放器) │
└─────────┘            └─────────┘               └─────────┘
```

### RTMP 推流配置

```bash
# FFmpeg RTMP 推流範例
ffmpeg -re \
  -i "pipe:0" \
  -c:v libx264 \
  -preset ultrafast \
  -tune zerolatency \
  -c:a aac \
  -ar 44100 \
  -f flv \
  "rtmp://live.example.com/app/streamkey"
```

### RTMP 參數優化

| 參數 | 推薦值 | 說明 |
|------|--------|------|
| preset | ultrafast | 最低編碼延遲 |
| tune | zerolatency | 零延遲模式 |
| keyint | 30-60 | 關鍵幀間隔 |
| 比特率 | 2500-4000 kbps | 平衡品質與頻寬 |

## WebRTC 架構

### 阿里雲 RTS 方案

```
┌─────────┐    WebRTC    ┌─────────┐    WebRTC    ┌─────────┐
│ 主播端   │ ─────────→  │   RTS   │ ──────────→  │  觀眾端  │
│         │   (UDP)     │  伺服器  │   (UDP)      │         │
└─────────┘             └─────────┘              └─────────┘
                              │
                    端到端延遲 < 1 秒
```

### WebRTC 特點

**優勢**：
- 超低延遲（< 500ms）
- 原生瀏覽器支援
- 雙向通訊

**挑戰**：
- 大規模分發困難
- NAT 穿透複雜
- 需要 STUN/TURN 伺服器

### WebRTC 前端實現

```javascript
// 建立 RTCPeerConnection
const config = {
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    { urls: 'turn:turn.example.com', credential: 'xxx' }
  ]
};

const pc = new RTCPeerConnection(config);

// 獲取媒體流
const stream = await navigator.mediaDevices.getUserMedia({
  video: { width: 1280, height: 720 },
  audio: true
});

// 添加軌道
stream.getTracks().forEach(track => {
  pc.addTrack(track, stream);
});

// 創建 Offer
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);

// 發送到信令伺服器...
```

## OBS 整合

### 虛擬攝像頭方案

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   數字人生成  │ →   │  虛擬攝像頭   │ →   │     OBS      │
│   (本地)     │     │  (OBS-VCam)  │     │   (推流)     │
└──────────────┘     └──────────────┘     └──────────────┘
```

### OBS 推流設定

```
設定 > 直播 > 服務：自訂
伺服器：rtmp://live.xxx.com/app
串流金鑰：your_stream_key

設定 > 輸出：
- 比特率：2500-4000 kbps
- 編碼器：x264 或 NVENC
- 關鍵幀間隔：2 秒
```

### NDI 方案（區網傳輸）

```
數字人電腦 ───NDI──→ OBS 電腦 ───RTMP──→ 直播平台
```

**優勢**：
- 區網內高品質傳輸
- 低延遲
- 多路輸入混合

### 彈幕處理策略

```python
# 彈幕意圖分類
INTENT_PATTERNS = {
    'price': ['多少錢', '價格', '價位', '貴不貴'],
    'stock': ['有貨嗎', '還有嗎', '庫存'],
    'quality': ['質量', '品質', '好不好'],
    'link': ['鏈接', '連結', '怎麼買'],
    'greeting': ['在嗎', '主播好', '來了'],
}

def classify_intent(message: str) -> str:
    for intent, patterns in INTENT_PATTERNS.items():
        if any(p in message for p in patterns):
            return intent
    return 'unknown'

# 優先級排序
def prioritize_messages(messages: list) -> list:
    priority = {
        'price': 1,    # 最高優先：直接促成交易
        'link': 2,
        'stock': 3,
        'quality': 4,
        'greeting': 5,
        'unknown': 6,  # 最低：可能需要 LLM 處理
    }
    return sorted(messages, key=lambda m: priority.get(m['intent'], 10))
```

## 監控與告警

### 關鍵指標

| 指標 | 告警閾值 | 說明 |
|------|----------|------|
| 推流延遲 | > 5s | 網路或編碼問題 |
| 丟幀率 | > 5% | 頻寬不足 |
| GPU 使用率 | > 90% | 需要擴容 |
| API 響應時間 | > 2s | LLM/TTS 瓶頸 |
| 彈幕處理延遲 | > 3s | 互動體驗下降 |

### 監控工具

- **Prometheus + Grafana**：指標監控
- **ELK Stack**：日誌分析
- **OBS 內建統計**：推流健康度
