# 品質標準：三條紅線與修正方向

## 付費課程的品質標準

**核心問題**：什麼叫「課程水準」？

**判斷標準**：
1. 讀者能否順利完成學習目標？
2. 讀者會不會覺得「值這個價錢」？
3. 讀者會不會推薦給其他人？

---

## 三條紅線

### 紅線 1: 太技術

**症狀**：
- Code snippet 太多（整頁都是 code）
- 術語沒解釋（假設讀者是專家）
- 讀起來像 API 文件或技術規格書
- 沒有「為什麼」，只有「怎麼做」

**實例（ECPay DLC v1 失敗版）**：
```markdown
❌ 太技術的寫法：

## Form Submit 機制

ECPay 使用 Form Submit 方式，需要在前端建立表單：

```html
<form id="payment-form" method="post" action="https://payment.ecpay.com.tw/...">
  <input type="hidden" name="MerchantID" value="...">
  <input type="hidden" name="MerchantTradeNo" value="...">
  <!-- 30+ 行參數 -->
</form>
<script>
  document.getElementById('payment-form').submit()
</script>
```

然後監聽 ReturnURL 和 OrderResultURL...
```

**為什麼這是問題**：
- 給了一大堆 code，但沒說「為什麼要這樣做」
- 讀者看完只會 copy-paste，不理解原理
- 跟主線課程的「點到為止」風格不一致

**修正方向**：
```markdown
✅ 改良版：

## 差異 3: ReturnURL 和 OrderResultURL 名字反過來

PAYUNi 的 ReturnURL 是「付款結果通知」，
ECPay 的 ReturnURL 反而是「付款完成後跳轉的頁面」。

**實際影響**：
如果你直接沿用 PAYUNi 的命名邏輯，會搞混這兩個 URL 的用途。

**怎麼做**：
重新確認你的 callback 函數是綁在哪個 URL 上。
```

---

### 紅線 2: 太水

**症狀**：
- 重複教主線已經教過的東西
- 沒有實質差異點，只是換個說法
- 篇幅很長，但資訊密度很低
- 讀者看完覺得「浪費時間」

**實例**：
```markdown
❌ 太水的寫法：

## 支付流程

首先，使用者會在你的網站上選擇商品，然後點擊「購買」按鈕。
這時候你的後端需要建立一筆訂單，訂單包含商品資訊、價格、使用者資料等。

接著，你要把訂單資訊傳給 ECPay，ECPay 會回傳一個支付頁面的網址。
你把使用者導向這個網址，使用者就可以在 ECPay 的頁面上輸入信用卡資料...

（繼續講完整流程，但這些主線都教過了）
```

**為什麼這是問題**：
- 主線課程已經講過完整流程
- DLC 讀者不需要重新學流程，他們要的是「差異點」

**修正方向**：
```markdown
✅ 改良版：

## 先說結論：流程沒變

建立訂單 → 導向支付頁 → Webhook 確認 → 開通權限

這個流程跟 PAYUNi 完全一樣。差別只在一些參數和編碼規則。
```

---

### 紅線 3: 人設崩壞

**症狀**：
- 語調跟主線課程差太多（主線朋友聊天風格，DLC 變成正式文件風格）
- Metaphor 風格不一致（主線都用生活比喻，DLC 突然用技術類比）
- 段落結構差異大（主線有預告下章，DLC 突然沒有）
- 讀者感覺「不像同一個老師寫的」

**實例**：
```markdown
❌ 人設崩壞的寫法：

# ECPay 金流整合技術文件

本文件旨在說明 ECPay 金流整合之技術規格與實作方式。
開發者應詳閱本文件，並依照規範進行整合作業。

## 1. 系統架構
ECPay 採用 Form Submit 機制，開發者需在前端建立表單...
```

**為什麼這是問題**：
- 主線課程是「朋友聊天」風格（你/我、口語化）
- DLC 突然變成「技術文件」風格（開發者、應、旨在）
- 讀者會覺得突兀，信任感下降

**修正方向**：
```markdown
✅ 改良版：

# ECPay 金流整合：八成一樣，差在哪？

你在 PAYUNi 學的那套，ECPay 有八成是一樣的。
這篇會告訴你那兩成的差異在哪，以及有哪些坑要注意。
```

## 修正方向判斷樹

收到不同的 feedback 時，該往哪個方向調整：

### Feedback: 「太跳」「很莫名」「閱讀體驗差」

**可能問題**：
1. 太技術（code 太多、術語沒解釋）
2. 風格不一致（語調跟主線差太多）

**診斷方法**：
- 檢查 code snippet 的比例（超過 30% = 太技術）
- 對比主線課程的語調（是否從朋友聊天變成正式文件？）

**修正方向**：
- 減少 code，只給關鍵差異
- 調整語調，對齊主線風格
- 加上「為什麼」，不只講「怎麼做」

---

### Feedback: 「太水」「沒什麼內容」

**可能問題**：
1. 重複教主線教過的東西
2. 沒有聚焦差異點

**診斷方法**：
- 逐段檢查：這段是在講「新的差異」還是「重複舊知識」？
- 問自己：如果讀者已經上過主線，這段還有價值嗎？

**修正方向**：
- 刪掉重複的流程說明
- 用「跟 X 一樣」快速帶過熟悉的部分
- 聚焦在「差異點」

---

### Feedback: 「不像同一門課」「感覺怪怪的」

**可能問題**：
人設崩壞（風格不一致）

**診斷方法**：
- 對比主線課程的：
  - 語調（你/我 vs 開發者/使用者）
  - Metaphor（日常 vs 技術）
  - 段落結構（有無預告下章）

**修正方向**：
- 重讀主線 2-3 章，重新對齊風格
- 調整用詞（改回第二人稱）
- 補上缺失的結構元素（如預告下章）

---

## 品質檢查清單

寫完初稿後,用這份清單自我檢查：

### 技術深度
- [ ] Code snippet 比例 < 30%
- [ ] 每個技術術語都有解釋或連結到主線
- [ ] 有「為什麼」，不只有「怎麼做」

### 內容價值
- [ ] 沒有重複教主線教過的完整流程
- [ ] 聚焦在「差異點」
- [ ] 每個段落都有實質資訊（不是廢話）

### 風格一致性
- [ ] 語調跟主線一致（用「你/我」）
- [ ] Metaphor 風格相符
- [ ] 段落結構一致（有預告下章）

### 可讀性
- [ ] 開頭有降焦慮（告訴讀者大部分是熟悉的）
- [ ] 差異點清晰（用「差異 1、2、3」結構）
- [ ] 有插圖標註位置

### DLC 定位
- [ ] 假設讀者已有前置知識（不從零教起）
- [ ] 可以獨立閱讀（不需要回頭翻主線）
- [ ] 有預告下篇（保持課程連貫）

## 成功案例：ECPay DLC v2

### v1 → v2 的修正

| 維度 | v1（失敗） | v2（成功） | 修正方向 |
|------|-----------|-----------|---------|
| 技術深度 | 大量 code snippet | 只給關鍵差異的 code | 減少 code，加上「為什麼」 |
| 內容價值 | 重複講流程 | 聚焦差異點 | 刪掉重複內容 |
| 風格 | 技術文件風格 | 朋友聊天風格 | 改用第二人稱、口語化 |
| 開頭 | 直接進技術細節 | 先降焦慮「八成一樣」 | 加上減焦慮開頭 |

### v2 的成功要素

1. **開頭降焦慮**：「先說結論：流程沒變」
2. **聚焦差異**：「那到底差在哪？差異 1、2、3」
3. **語調一致**：保持「你/我」第二人稱
4. **技術深度適當**：只給關鍵差異的 code，不給完整實作
5. **有預告下篇**：保持課程連貫性

## 更新原則

- 發現新的品質問題類型時，新增到「三條紅線」
- 累積新的 feedback 判斷案例時，更新「修正方向判斷樹」
- 有新的成功案例時，補充到「成功案例」區塊
- 檢查清單需要新增項目時，更新「品質檢查清單」
