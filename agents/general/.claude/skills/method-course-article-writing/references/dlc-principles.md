# DLC 原則：DLC vs 主線的本質差異

## 什麼是 DLC

**DLC (Downloadable Content)**：在遊戲界指「額外下載內容」，在課程中指「主線課程的補充內容」

**課程 DLC 的特性**：
- 購買者通常已完成主線課程
- 內容是主線的延伸或補充，不是核心必修
- 可以獨立定價、獨立銷售

---

## DLC vs 主線：四個本質差異

### 差異 1: 讀者的心理狀態不同

| | 主線課程 | DLC |
|--|---------|-----|
| 心理狀態 | 「我要學新東西」 | 「我已經會了，這個有什麼不一樣？」 |
| 焦慮來源 | 怕學不會 | 怕又要重新學一套 |
| 期待 | 從零開始教 | 告訴我差異點就好 |

**寫作策略**：
- 主線：循序漸進建立知識
- DLC：**先降焦慮**（告訴他們大部分是一樣的），**再聚焦差異**

---

### 差異 2: 前置知識的假設

| | 主線課程 | DLC |
|--|---------|-----|
| 假設 | 讀者什麼都不知道 | 讀者已經懂主線教的概念 |
| 術語 | 要解釋 | 可以直接用（因為主線已經建立） |
| 範例 | 要從基礎開始 | 可以跳過基礎，直接講進階 |

**寫作策略**：
- 主線：建立術語系統（如「父單子單」）
- DLC：**直接使用主線建立的術語**，不用重新解釋

**實例**：
```
❌ DLC 重新解釋：「父單代表訂閱合約，子單代表每次扣款...」
✅ DLC 直接用：「跟 PAYUNi 一樣，這裡也是父單子單架構」
```

---

### 差異 3: 內容深度的定位

| | 主線課程 | DLC |
|--|---------|-----|
| 目標 | 建立完整知識體系 | 補充特定場景或工具 |
| 深度 | 核心概念要講透 | 只講「這個工具特有的坑」 |
| 廣度 | 涵蓋整個主題 | 聚焦在差異點 |

**寫作策略**：
- 主線：「Webhook 是什麼？為什麼需要？怎麼實作？」（完整教）
- DLC：「Webhook 跟 PAYUNi 一樣重要，但 ECPay 的 ReturnURL 命名反過來了」（只講差異）

---

### 差異 4: 學習目標不同

| | 主線課程 | DLC |
|--|---------|-----|
| 學習目標 | 「學會整合支付系統」 | 「知道 ECPay 跟 PAYUNi 的差異」 |
| 成功標準 | 能從零實作 | 能快速切換到新工具 |
| 價值主張 | 建立核心能力 | 降低遷移成本 |

**寫作策略**：
- 主線：「學完這章你就會整合支付」
- DLC：「學完你就知道從 PAYUNi 切到 ECPay 要改哪些地方」

---

## DLC 的三個寫作原則

### 原則 1: 開頭先降焦慮

**人性**：看到「新的工具」會下意識覺得「又要重新學一套」

**策略**：第一段就告訴讀者「大部分是一樣的」

**模板**：
```markdown
## 先說結論：XX% 一樣

[核心概念] 沒變：
- [概念 1] 的用途？[一句話]
- [概念 2] 的重要性？[一句話]

那到底差在哪？
```

**ECPay DLC 實例**：
```markdown
## 先說結論：流程沒變

CheckMacValue 的用途？**防止資料被竄改**。
Webhook 的重要性？**唯一可信的狀態來源**。

那到底差在哪？
```

---

### 原則 2: 用「差異對比」而非「完整流程」

**為什麼**：讀者已經懂流程，重複講流程 = 浪費時間

**策略**：用對比表格或條列式差異點

**模板**：
```markdown
## 差異 1: [具體差異點]

**PAYUNi**: [A 的做法]
**ECPay**: [B 的做法]

**為什麼不同**：[原因]
**實際影響**：[這會導致什麼坑]
```

**ECPay DLC 實例**：
```markdown
## 差異 1: 空格會害你驗證失敗

**PAYUNi**: JavaScript 的 `encodeURIComponent` 把空格編碼為 `%20`
**ECPay**: .NET 風格，要把空格編碼為 `+`

**為什麼不同**: ECPay 後端是 .NET，URL 編碼規則不同
**實際影響**: 如果用錯，CheckMacValue 會對不上 → 交易失敗
```

---

### 原則 3: 給決策樹，不給流程圖

**為什麼**：DLC 讀者需要的不是「怎麼做」（主線教過了），而是「這個情境該選什麼」

**流程圖 vs 決策樹**：
```
❌ 流程圖：步驟 1 → 步驟 2 → 步驟 3
   （主線已經教過了，不用重複）

✅ 決策樹：
   Q: 賣的是數位商品？
   └─ 是 → Print=0, CarrierType=1
   Q: 需要給實體發票？
   └─ 是 → Print=1
```

**ECPay 發票 DLC 實例**：
```markdown
## 關鍵決策：Print 和 CarrierType

**數位商品**（推薦）：
- Print = 0（不列印紙本）
- CarrierType = 1（ECPay 載具）
- 只需要 Email

**需要實體發票**：
- Print = 1
- 會多一筆郵寄成本
```

## 何時打破這些原則

### 例外 1: 這是全新概念

**情境**：主線沒教過，DLC 才引入（如「電子發票」）

**做法**：可以從基礎講起，但要說明「這是新增的維度」

**實例**：
```markdown
## 電子發票整合：新的維度

主線課程講的是「金流」，這篇要講的是「發票」。
這是兩個獨立的系統，但通常會一起整合。
```

### 例外 2: 主線講得不夠清楚

**情境**：主線只是帶過，DLC 需要深入

**做法**：可以重新講一次，但要說明「主線簡化了，這裡補充細節」
