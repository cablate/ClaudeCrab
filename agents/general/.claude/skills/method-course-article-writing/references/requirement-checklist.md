# 需求確認清單：5 問確認法

## 為什麼需要這個清單

**問題**：開始寫之前沒有對齊需求 → 寫完被打槍 → 重寫浪費時間

**解法**：用 5 個問題在動筆前確認清楚「到底要寫什麼」

---

## 5 個核心問題

### 問題 1：融合 vs 獨立？

**問的是**：這篇 DLC 是主線課程的「延續」還是「獨立章節」？

**為什麼問**：
- **融合性質**：讀者預設已上過主線課程，不用重複教基礎概念
- **獨立性質**：可能有人跳著買 DLC，需要補充必要的前置知識

**範例回答**：
- 「是融入性質，也是額外 DLC，預設大家已經上過前面的課程」
- 「獨立成章，但會在開頭簡單回顧前置知識」

**影響**：
- 融合 → 可以大量使用「跟第 X 章一樣」的說法
- 獨立 → 需要補充基礎概念摘要

---

### 問題 2：目標受眾？

**問的是**：預設讀者已經有什麼程度的前置知識？

**為什麼問**：
- 避免「對新手講太深」或「對老手重複教基礎」
- 確定技術術語是否需要解釋

**範例回答**：
- 「已完成課程主線」
- 「有基礎程式經驗，但沒上過課程」
- 「完全新手」

**影響**：
- 已完成主線 → 可以直接用課程建立的術語（如「父單子單」）
- 新手 → 術語要解釋，metaphor 要更日常

---

### 問題 3：交付格式？

**問的是**：最終產出是什麼形式？

**選項**：
- A. 影片腳本（要口語化、有停頓點、配合畫面）
- B. 純文章（可以用 markdown、code block、插圖標註）
- C. 簡報投影片（精簡條列、視覺優先）
- D. 互動式教材（有練習題、checkpoint）

**範例回答**：
- 「B，純文章教學文章 + 插圖標註」

**影響**：
- 影片腳本 → 要寫「現在你看到畫面上...」
- 純文章 → 可以用 code block、決策樹、表格
- 簡報 → 每頁一個重點，不能有大段落

---

### 問題 4：內容拆分？

**問的是**：這個主題要寫成一篇，還是拆成多篇？

**為什麼問**：
- 避免一篇文章塞太多東西（讀者看到一半放棄）
- 確定每篇的範圍邊界

**範例回答**：
- 「拆成兩篇文章：第一篇講金流整合，第二篇講電子發票」
- 「一篇搞定，但分成三個大段落」

**影響**：
- 拆成多篇 → 每篇要能獨立閱讀，但要預告下篇
- 一篇搞定 → 要有清晰的段落分隔，避免資訊過載

---

### 問題 5：技術深度？

**問的是**：要給到什麼程度的技術細節？

**為什麼問**：
- 避免「給太多 code 變成 API 文件」或「太淺變成廢話文」

**光譜**：
```
完整實作 ←→ 點到為止
(給 code)    (講概念 + 關鍵參數)
```

**範例回答**：
- 「點到為止，PAYUNi 都有提過且講解過了」
- 「給完整 code，這是全新的概念」

**影響**：
- 點到為止 → 只講「差異點」和「關鍵參數」
- 完整實作 → 給 code snippet + 逐行解釋

## 實戰案例：ECPay DLC

| 問題 | 使用者回答 | 設計決策 |
|------|-----------|---------|
| 1. 融合 vs 獨立？ | 「融入性質，預設已上過課程」 | 大量使用「跟 PAYUNi 一樣」，不重複教基礎 |
| 2. 目標受眾？ | 「已完成課程主線」 | 可以直接用課程術語（父單子單、Webhook） |
| 3. 交付格式？ | 「B，純文章 + 插圖標註」 | 用 markdown 表格、決策樹、code snippet |
| 4. 內容拆分？ | 「拆成兩篇：金流 + 發票」 | 每篇獨立但有預告，避免單篇過長 |
| 5. 技術深度？ | 「點到為止，都講過了」 | 只講差異點（%20 vs +、測試卡號、參數差異） |

## 使用時機

**何時用**：
- 開始撰寫任何課程 DLC 之前
- 需求不明確時（寧可多問，不要猜）

**何時不用**：
- 主線課程核心章節（那有獨立的規劃流程）
- 需求已經非常明確且有詳細 spec 的情況

---

## 更新原則

當發現「5 個問題不夠用」或「某個問題問錯重點」時更新：
- 新增問題：發現有其他關鍵需求沒被涵蓋
- 調整選項：某個問題的選項不夠清楚
- 補充案例：累積新的實戰案例
