# 架構工具包

## 工具 1: 減焦慮開頭

### 為什麼需要

**人性**：看到「新的整合」「新的工具」會下意識焦慮 →「又要重新學一套？」

**目標**：第一段就讓讀者放心「大部分是熟悉的，只有少數差異」

### 模板

```markdown
## 先說結論：[核心概念] 沒變

[概念 1] 的用途？[一句話答案]
[概念 2] 的重要性？[一句話答案]

那到底差在哪？
```

### 變化版本

**版本 1: 百分比法**
```markdown
## 先說結論：八成一樣

你在 PAYUNi 學的那套流程，ECPay 有 80% 是一模一樣的。
差異只在這三個地方...
```

**版本 2: 核心不變法**
```markdown
## 核心邏輯沒變

建立訂單 → 導向支付頁 → Webhook 確認 → 開通權限

這個流程完全一樣，只是細節有些差異。
```

**版本 3: 問答法**（ECPay DLC 實際使用）
```markdown
## 先說結論：流程沒變

CheckMacValue 的用途？**防止資料被竄改**。
Webhook 的重要性？**唯一可信的狀態來源**。

那到底差在哪？
```

### 使用時機

- DLC 文章的第一段
- 介紹「替代工具」時（如 ECPay vs PAYUNi）
- 讀者可能焦慮「又要重新學」的場景

## 工具 2: 差異點聚焦

### 結構

```markdown
## 差異 1: [具體、可操作的差異點]

[一句話說明這個差異]

**為什麼不同**：[技術原因]
**實際影響**：[這會導致什麼問題]
**怎麼做**：[具體解法]

## 差異 2: ...
## 差異 3: ...
```

### 實例：ECPay DLC

```markdown
## 差異 1: 空格會害你驗證失敗

ECPay 的 CheckMacValue 計算，對空格的編碼方式跟 PAYUNi 不同。

**為什麼不同**：
- JavaScript: 空格 → `%20` ❌
- .NET 風格: 空格 → `+` ✅

**實際影響**：
如果你用 JavaScript 的 `encodeURIComponent`，
CheckMacValue 會對不上 → 交易失敗

**怎麼做**：
檢查你的編碼函數，確保空格是編碼成 `+` 而不是 `%20`
```

### 關鍵原則

- **標題要具體**：不是「差異 1: 編碼」，而是「差異 1: 空格會害你驗證失敗」
- **先講影響**：讀者關心的是「這會導致什麼問題」，不是技術細節
- **可操作**：要給出「怎麼做」，不是只講「是什麼」

## 工具 3: 決策樹

### 何時用

DLC 讀者已經懂流程，他們需要的是「這個情境該選什麼」

### 模板

```markdown
## 關鍵決策：[參數名稱]

**情境 A**（推薦）：
- [參數 1] = [值]
- [參數 2] = [值]
- 適用：[什麼場景]

**情境 B**：
- [參數 1] = [值]
- [參數 2] = [值]
- 適用：[什麼場景]
```

### 實例：ECPay 電子發票

```markdown
## 關鍵決策：Print 和 CarrierType

**數位商品**（推薦）：
- Print = 0（不列印紙本）
- CarrierType = 1（ECPay 電子發票載具）
- 只需要使用者的 Email

**需要實體發票**：
- Print = 1
- 會多一筆郵寄成本
- 適合賣實體商品的場景
```

### 決策樹 vs 流程圖

| | 流程圖 | 決策樹 |
|--|-------|-------|
| 適用 | 主線課程（建立流程概念） | DLC（讀者已懂流程，需要選擇） |
| 呈現 | 時間順序（步驟 1→2→3） | 情境選擇（if A then X, if B then Y） |
| 焦點 | 「怎麼做」 | 「選什麼」 |

## 工具 4: 插圖標註

### 為什麼需要

純文字描述技術細節容易抽象，插圖可以讓讀者快速理解

### 標註方式

```markdown
**【插圖建議：XXX】**
- 內容：[插圖要呈現什麼]
- 標註：[哪些地方要特別標出來]
```

### 實例：ECPay DLC

```markdown
## 差異 3: ReturnURL 和 OrderResultURL 名字反過來

**【插圖建議：PAYUNi vs ECPay 參數對比表】**
- 內容：兩欄對比，左邊 PAYUNi，右邊 ECPay
- 標註：用箭頭標出「ReturnURL 在 ECPay 是付款完成頁」
```

### 常見插圖類型

| 類型 | 適用場景 | 範例 |
|------|---------|------|
| 對比表 | 說明差異 | PAYUNi vs ECPay 參數對比 |
| 決策樹圖 | 幫助選擇 | Print/CarrierType 組合選擇 |
| 流程圖 | 說明新流程 | 電子發票「開立 → 發送通知」兩步驟 |
| 截圖標註 | 介面操作 | 測試環境的測試卡號輸入位置 |
| 程式碼片段 | 關鍵差異 | 空格編碼的正確 vs 錯誤寫法 |

## 工具 5: 預告下章

### 為什麼需要

**目標**：保持課程的連貫性，讓讀者知道「學完這篇接下來學什麼」

### 模板

```markdown
## 下一篇

這篇講的是 [主題 A]，下一篇我們會講 [主題 B]。

[一句話說明為什麼 B 是自然的下一步]
```

### 實例：ECPay 金流整合 → 電子發票整合

```markdown
## 下一篇：電子發票整合

金流整合完成後，接下來就是「開立發票」。

台灣法規規定，營業額超過一定門檻就必須開發票。
下一篇會講 ECPay 的電子發票整合，以及跟金流的串接方式。
```

### 變化版本

**版本 1: 遺留問題法**
```markdown
## 下一篇

這篇我們略過了「訂閱制」的部分，因為 ECPay 的訂閱制跟一次性支付有些不同。

下一篇會專門講 ECPay 的訂閱制整合。
```

**版本 2: 進階挑戰法**
```markdown
## 下一篇

目前我們講的是「單一金流」，但實際上很多產品會同時接 2-3 家金流。

下一篇會講「多金流架構設計」，怎麼讓系統優雅地支援多個支付服務。
```

## 工具 6: 對比表格

### 何時用

需要快速呈現「A vs B」的差異

### 模板

```markdown
| | [方案 A] | [方案 B] |
|--|---------|---------|
| [維度 1] | [A 的特性] | [B 的特性] |
| [維度 2] | [A 的特性] | [B 的特性] |
| 適用場景 | [什麼時候用 A] | [什麼時候用 B] |
```

### 實例：Print 參數選擇

```markdown
| | Print = 0 | Print = 1 |
|--|-----------|-----------|
| 發票形式 | 電子發票 | 紙本發票 |
| 使用者需提供 | Email | 郵寄地址 |
| 額外成本 | 無 | 郵資 + 印刷 |
| 適用場景 | 數位商品 | 實體商品 |
```

## 工具使用組合

**典型 DLC 文章結構**：

```markdown
# [DLC 主題]

## 先說結論：XX% 一樣                   ← 工具 1: 減焦慮開頭
[核心概念沒變]

## 差異 1: [具體差異點]                 ← 工具 2: 差異點聚焦
[為什麼不同 + 實際影響 + 怎麼做]

**【插圖建議：...】**                   ← 工具 4: 插圖標註

## 差異 2: ...

## 關鍵決策：[參數選擇]                  ← 工具 3: 決策樹
[情境 A vs 情境 B]

| | 方案 A | 方案 B |                    ← 工具 6: 對比表格
|--|--------|--------|

## 下一篇                                ← 工具 5: 預告下章
[接下來要學什麼]
```

## 更新原則

- 發現新的有效架構模式時，新增到工具包
- 累積到 3+ 個使用案例時,補充「實例」區塊
- 發現工具的變化版本時，補充到對應工具的「變化版本」
