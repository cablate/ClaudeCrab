## Phase 1: 需求分析

### 5 問確認

| 問題 | 使用者回答 | 影響 |
|------|-----------|------|
| 1. 融合 vs 獨立？ | 「融入性質，也是額外 DLC，預設大家已經上過前面的課程」 | 不用重複教基礎概念 |
| 2. 目標受眾？ | 「已完成課程主線」 | 可以直接用課程術語（父單子單、Webhook） |
| 3. 交付格式？ | 「B，純文章教學文章 + 插圖標註」 | 用 markdown、決策樹、code snippet |
| 4. 內容拆分？ | 「拆成兩篇文章」 | 第一篇金流、第二篇發票 |
| 5. 技術深度？ | 「點到為止啊，你舉例的東西其實 Payuni 都有提過且講解過了」 | 只講差異點，不重複完整實作 |

### 設計決策

基於 5 問的回答：
- **定位**：DLC 補充內容，預設讀者已完成主線
- **風格**：對齊主線的朋友聊天風格
- **深度**：點到為止，聚焦差異
- **結構**：每篇獨立但有預告，避免單篇過長

## Phase 4: 初稿撰寫（v1 失敗版）

### v1 的問題

**使用者反饋**：
> 「跟原本文章的閱讀體驗差太多，很跳，很莫名，不像是一篇付費線上課程的水準，而且講一堆難以閱讀的技術內容」

**問題診斷**：

1. **太技術**：
   - 給了大量 code snippet（Form Submit 的完整 HTML）
   - 過度強調實作細節（程式流程差異）

2. **沒有降焦慮**：
   - 直接進入技術細節
   - 沒有告訴讀者「大部分是一樣的」

3. **風格不一致**：
   - 語調變成技術文件風格
   - 失去主線的朋友聊天感

### v1 失敗片段範例

```markdown
❌ v1 的寫法：

## Form Submit vs API Redirect

### PAYUNi 的做法
PAYUNi 使用 API redirect 方式，你的後端呼叫 API 取得支付網址，
然後把使用者導向該網址。

### ECPay 的做法
ECPay 使用 Form Submit，需要在前端建立表單：

```html
<form id="payment-form" method="post" action="...">
  <input type="hidden" name="MerchantID" value="...">
  <input type="hidden" name="MerchantTradeNo" value="...">
  <!-- 30+ 行參數 -->
</form>
```

這導致你需要調整前端的邏輯...
```

**為什麼失敗**：
- 把實作細節（Form Submit vs API）當核心差異
- 實際上業務邏輯是一樣的，只是技術實現不同
- 給了太多 code，但沒說「為什麼這個差異重要」

## Phase 5: 修正（v2 成功版）

### 修正方向

1. **開頭先降焦慮**
2. **聚焦實務差異，不是實作細節**
3. **只給會踩坑的地方，不給完整流程**

### v2 成功片段

```markdown
✅ v2 的寫法：

# ECPay 金流整合：八成一樣，差在哪？

## 先說結論：流程沒變

CheckMacValue 的用途？**防止資料被竄改**。
Webhook 的重要性？**唯一可信的狀態來源**。

從「使用者選擇商品 → 付款 → 開通權限」這整個商業邏輯來看，
ECPay 跟 PAYUNi 沒有任何差別。

那到底差在哪？

## 差異 1：空格會害你驗證失敗

這是最容易踩的坑。

**問題**：
如果你的商品名稱是 "Apple iPhone"（中間有空格），
ECPay 的 CheckMacValue 計算會跟你想的不一樣。

**原因**：
- JavaScript 的 `encodeURIComponent` 會把空格編碼成 `%20`
- 但 ECPay 後端用的是 .NET，它把空格編碼成 `+`

**實際影響**：
你算出來的 CheckMacValue 會對不上 → 交易失敗

**怎麼做**：
檢查你的 URL 編碼函數，確保空格是 `+` 而不是 `%20`
```

### v2 vs v1 對比

| 維度 | v1 | v2 | 改善 |
|------|----|----|------|
| 開頭 | 直接講技術 | 先降焦慮「八成一樣」 | ✅ |
| 差異點 | Form Submit vs API（實作細節） | 空格編碼、測試卡號（實務坑點） | ✅ |
| Code 比例 | ~40%（大量 HTML） | ~10%（只給關鍵差異） | ✅ |
| 語調 | 技術文件風格 | 朋友聊天風格 | ✅ |
| 為什麼 | 缺少 | 每個差異都解釋「為什麼重要」 | ✅ |

### 使用者反饋（v2）

> 「好多了」

## 成功要素總結

### 1. 需求對齊

**5 問確認法**避免了：
- 「我以為你要 A，結果你要 B」
- 寫完才發現技術深度不對
- 風格定位錯誤

### 2. 風格對齊

**讀主線 2-3 章**確保了：
- 語調一致（朋友聊天，不是技術文件）
- 技術深度一致（點到為止，不是完整實作）
- 結構一致（有預告下章）

### 3. 減焦慮開頭

**「先說結論：流程沒變」**達成：
- 讀者不焦慮「又要重新學一套」
- 明確設定期待「只需關注差異」
- 快速進入重點

### 4. 聚焦實務差異

**不是講實作細節，而是講會踩的坑**：
- 空格編碼（會導致驗證失敗）
- 測試卡號（不知道就測不了）
- 參數命名（容易搞混）

### 5. 決策樹 > 流程圖

**DLC 讀者已經懂流程**：
- 不用重複講「步驟 1→2→3」
- 給「這個情境該選什麼」（Print/CarrierType 決策樹）

## 可複用的模式

### 模式 1: 減焦慮開頭（問答式）

```markdown
## 先說結論：[核心概念] 沒變

[概念 A] 的用途？[一句話答案]
[概念 B] 的重要性？[一句話答案]

那到底差在哪？
```

### 模式 2: 差異點結構

```markdown
## 差異 X: [具體問題]

**問題**：[會遇到什麼狀況]
**原因**：[為什麼會這樣]
**實際影響**：[不處理會怎樣]
**怎麼做**：[具體解法]
```

### 模式 3: 決策樹（表格式）

```markdown
## 關鍵決策：[參數名]

| | 選項 A | 選項 B |
|--|--------|--------|
| 參數設定 | X=1, Y=0 | X=0, Y=1 |
| 適用場景 | [什麼情境] | [什麼情境] |
| 注意事項 | [要注意什麼] | [要注意什麼] |
```

## 經驗教訓

### 教訓 1: 不要把實作細節當核心差異

**錯誤思維**：「Form Submit 跟 API Redirect 不同 → 這是核心差異」  
**正確思維**：「業務邏輯一樣，只是技術實現不同 → 讀者不用關心」

### 教訓 2: DLC 的價值在「降低遷移成本」

**讀者要的不是**：「怎麼從零整合 ECPay」（那是主線課程的事）  
**讀者要的是**：「我已經會 PAYUNi，切到 ECPay 要注意什麼」

### 教訓 3: 風格比內容更容易出問題

**技術正確 ≠ 好的課程內容**：
- v1 技術上沒錯，但風格不對 → 被打槍
- v2 技術內容差不多，但風格對了 → 通過

### 教訓 4: 開頭決定成敗

**讀者前 30 秒的感受**：
- v1: 「又要重新學？好煩...」
- v2: 「喔八成一樣啊，那我只要注意這三個差異就好」

## 適用範圍

這套方法適用於：
- ✅ 線上課程的 DLC 補充內容
- ✅ 「A 工具 vs B 工具」的差異說明
- ✅ 預設讀者已有前置知識的進階教學

不適用於：
- ❌ 主線課程的核心章節（那需要從零建立知識）
- ❌ 獨立的技術文章（不預設讀者有特定前置知識）
- ❌ 講座講義或 Workshop 教材（互動性質不同）
