# SOP 08：AI 系統開發案

**版本**：v1.0
**建立日期**：2026-03-17
**最後更新**：2026-03-17

---

## 觸發條件

B 端客戶確認 AI 系統開發需求，雙方初步達成合作意向，進入正式規劃階段。

---

## 流程圖

```
[客戶確認開發需求]
        ↓
[業務助理] 整理需求文件（3 天）
        ↓
[秘書] 可行性評估 + 資源分配
        ↓
[Cab] 架構決策 + 報價確認
        ↓
    簽約確認
        ↓
[Coder] 開發（里程碑制）
        ↓  ←── 每里程碑
[Cab] Code Review + 關鍵決策
        ↓
[業務助理] 交付 + 客戶驗收
        ↓
[業務助理] 後續維護提案
```

---

## 詳細步驟

### Step 1：需求整理

| 項目 | 內容 |
|------|------|
| **負責人** | 業務助理 |
| **輸入** | 客戶諮詢紀錄、初步討論記錄 |
| **動作** | 與客戶確認並文件化：功能需求清單、系統邊界（範疇）、時程期望、預算上限 |
| **輸出** | 需求規格文件（功能 + 範圍 + 時程 + 預算） |
| **品質檢查點** | 需求明確到可以報價（每個功能有驗收標準）；範圍邊界清楚（哪些「不做」也要說清楚）；預算有明確數字 |
| **時限** | 客戶確認開發需求後 3 天 |

### Step 2：可行性評估

| 項目 | 內容 |
|------|------|
| **負責人** | 秘書 |
| **輸入** | 需求規格文件 |
| **動作** | 評估技術風險（有沒有未知的技術挑戰）；資源分配（Coder 工時估算）；時程可行性（客戶期望 vs 實際可行） |
| **輸出** | 可行性評估報告（技術風險 + 資源需求 + 時程估算 + 是否接案建議） |
| **品質檢查點** | 技術風險有識別（不是「沒問題」）；工時估算有依據；風險與緩解措施對應 |
| **時限** | 收到需求規格後 2 天 |

### Step 3：架構決策與報價確認

| 項目 | 內容 |
|------|------|
| **負責人** | Cab |
| **輸入** | 需求規格 + 可行性評估 |
| **動作** | 決定技術架構選型（模型、框架、基礎設施）；確認開發範疇；核定最終報價 |
| **輸出** | 架構決策文件（技術選型 + 理由）；最終報價（Cab 簽核） |
| **品質檢查點** | 技術選型有明確理由；報價 Cab 親自確認 |
| **時限** | 收到可行性評估後 2 天 |

*架構決策與報價確認後，送業務助理與客戶簽約。*

### Step 4：開發執行

| 項目 | 內容 |
|------|------|
| **負責人** | Coder |
| **輸入** | 開發任務包（需求規格 + 架構決策 + 技術約束） |
| **動作** | 依照里程碑計畫開發；遵循 dev-workflow skill；每週進度回報；完成後輸出技術文件 |
| **輸出** | 功能實作 + 單元測試 + 技術文件（逐里程碑交付） |
| **品質檢查點** | 遵循 dev-workflow skill 規範；測試通過；文件與代碼同步更新；每週進度回報不漏 |
| **時限** | 依合約時程；每週進度回報 |

### Step 5：Code Review 與關鍵決策

| 項目 | 內容 |
|------|------|
| **負責人** | Cab |
| **輸入** | 每個里程碑的交付物 |
| **動作** | 審查代碼品質、架構合理性；針對技術岔路做出決策 |
| **輸出** | Review 意見（通過 / 修改清單 / 架構調整決策） |
| **頻率** | 每個里程碑結束時（不跳過） |
| **時限** | 收到里程碑交付物後 2 天 |

### Step 6：交付與客戶驗收

| 項目 | 內容 |
|------|------|
| **負責人** | 業務助理 |
| **輸入** | 完整系統 + 技術文件 |
| **動作** | 準備交付包；協助客戶驗收（對照需求規格逐項確認）；收集驗收簽核 |
| **輸出** | 交付文件包（功能說明 + 操作手冊 + 源碼）；驗收簽核書 |
| **品質檢查點** | 驗收清單全過（每項功能對照需求規格確認）；操作手冊學員可獨立操作 |
| **時限** | 開發完成後 3 天完成交付 |

### Step 7：後續維護提案

| 項目 | 內容 |
|------|------|
| **負責人** | 業務助理 |
| **輸入** | 驗收完成確認 |
| **動作** | 提出維護方案（維護範圍、回報頻率、報價）；推薦後續合作方案（升級、新功能、員工培訓） |
| **輸出** | 維護提案書 |
| **時限** | 驗收完成後 1 週內發送 |

## 交接規範

| 交接 | 交付物 | 驗收標準 |
|------|--------|----------|
| 業務助理 → 秘書 | 需求規格文件 | 功能/範圍/時程/預算四項齊全，可報價 |
| 秘書 → Cab | 可行性評估報告 + 需求規格 | 風險識別、工時估算、是否接案建議清楚 |
| Cab → 秘書 | 架構決策 + 報價 | 技術選型明確，報價 Cab 親簽 |
| 秘書 → Coder | 開發任務包（需求 + 架構 + 技術約束 + 里程碑計畫） | Coder 拿到就能開始，無需反覆確認 |
| Coder → 業務助理 | 交付物包（系統 + 技術文件 + 操作手冊 + 源碼） | 文件完整，可獨立驗收 |

## 異常處理

| 情況 | 處理方式 |
|------|----------|
| 開發過程中客戶追加需求 | 業務助理評估影響（工時 + 時程）；變更幅度 > 10% 工時則重新報價並更新合約；小幅調整（< 10%）記錄在案，作為下一期議題 |
| 技術方案不可行 | Coder 提出替代方案（至少 2 個選項，含優缺點）；秘書評估對需求的影響；Cab 做最終決策 |
| 驗收不通過 | Coder 修復；合約約定最多 2 輪修改（超過 2 輪則作為新需求評估追加費用）；業務助理管理客戶期待 |
| Coder 開發嚴重延期（> 1 週） | 秘書評估影響範圍；Cab 決定是否需要調整架構或需求；業務助理主動與客戶溝通時程調整 |
| 客戶在驗收後提出重大修改 | 確認是否屬於原始需求範圍；屬於範圍內的缺陷：Coder 修復；屬於新需求：作為新案評估 |

## 品質指標

| 指標 | 目標值 | 量測方式 |
|------|--------|----------|
| 按時交付率 | ≥ 90% | 里程碑時間追蹤 |
| 驗收一次通過率 | ≥ 80% | 驗收記錄統計 |
| 客戶追加需求的處理時間 | ≤ 2 天（評估結果回覆客戶） | 業務助理記錄 |
| Code Review 覆蓋率 | 100%（每個里程碑都有 Review） | Cab 確認 |
