## 案例 1：課程推廣（Threads）

### 原文

```
閒聊台結束直接睡死，睡到剛剛
三個鬧鐘都沒叫醒我🫥🫥

我與數位簡報室有合作一個為期四週的線上直播課，每週都有一場兩小時的直播，總共會有四場與 Vibe/AI Coding、產品、金流、資安、以及 AI 工具使用的 MCP/Skill 等主題。

課程期間我們有學員社群，不論是想聊產品還是聊開發，只要不跑題(?)我都會跟你交流。

如果你才剛開始接觸，不熟開發領域的知識、不清楚自己究竟需要什麼，想要有人可以問與交流，那這堂課絕對適合你，而且我覺得很划算。

有興趣的話留言 +1 讓我知道！
```

### 評分

| 維度 | 分數 | 評價 |
|------|------|------|
| 真實感與親和力 | 9/10 | 開頭用睡過頭破冰，非常自然 |
| 權威感與背書 | 7/10 | 有合作夥伴背書，但缺乏數位簡報室說明 |
| 關鍵字佈局 | 8/10 | Vibe、AI Coding、MCP 都是熱門關鍵字 |
| 痛點直擊 | 8/10 | 精準定義受眾（剛開始、不熟悉） |
| 附加價值 | 7/10 | 強調社群陪伴，但「划算」太主觀 |
| 行動呼籲 | 10/10 | +1 超低門檻，完美 |

**總分：49/60**

### 使用的手法

- ✅ 個人糗事破冰（睡過頭）
- ✅ 合作夥伴背書（數位簡報室）
- ✅ 熱門關鍵字佈局（AI、MCP、Vibe）
- ✅ 明確定義受眾（剛開始接觸、不熟悉）
- ✅ 強調社群互動（「我都會跟你交流」）
- ✅ 低門檻 CTA（+1）

### 可優化的地方

1. **強化權威背書** — 「數位簡報室」對不認識的人缺乏說服力
   - 建議：加上數位簡報室的公信力或自己的專業標籤
   - 範例：「數位簡報室(台灣最大簡報社群)」

2. **具象化「划算」** — 「我覺得很划算」太主觀
   - 建議：用數據或對比呈現 CP 值
   - 範例：「四週八小時直播 + 一個月社群陪伴，平均一小時不到一杯咖啡錢」

3. **優化資訊排版** — 課程主題那句太長太擠
   - 建議：用條列或精簡描述
   - 範例：「涵蓋：AI Coding 實戰、產品規劃、金流串接、資安防護、MCP/Skill 應用」

## 案例 2：人設建立（Telegram 私域社群）

### 原文（使用者最終版）

```
最近因為自製龍蝦，所以也跟想自製的人有交流，工程師們真的很喜歡自己動手🤣

我會混跡的私域社群不多，我在這些社群中待久了，我就會開始有問必答（？）

例如前幾天 @__i.change 先起頭問我龍蝦的架構怎麼搓的、難度有多高；
接著是 @cyesuta.lee 也加入話題，提出他目前的需求與構思過程中卡關的點。

從去年到現在 Agent 的這類管理需求與問題還是沒什麼太大的變化，門檻其實逐漸降低，Agent 套件也是越來越多，以往還要手搓對話，現在套件都幫你處理完了，串個接口的事情而已。

所以還是能幫就幫，大家就是互相幫忙。
```

### 評分

| 維度 | 分數 | 評價 |
|------|------|------|
| 真實感與親和力 | 8/10 | 自然調性，emoji 使用恰當 |
| 權威感與背書 | 6/10 | 有技術觀察，但「龍蝦」暱稱對外人不友善 |
| 關鍵字佈局 | 4/10 | 缺少框架說明，SEO 弱 |
| 痛點直擊 | 7/10 | 產業觀察精準 |
| 附加價值 | 6/10 | 有洞察但不深 |
| 行動呼籲 | 3/10 | 輕量互動（符合人設文定位）|

**總分：34/60**

### 關鍵判斷

**34/60 對於人設建立文是合理分數**，不需要追求導流文的高分。

- ✅ 真實感足夠（8 分）
- ✅ 有價值洞察（6 分）
- ✅ CTA 輕量（3 分，符合人設文特性）

### 使用的手法

- ✅ 真實情境開場（自製龍蝦、工程師自己動手）
- ✅ 展示「大方/樂於分享」人設（有問必答）
- ✅ 具名標記（@提及，增加真實感）
- ✅ 產業觀察（Agent 套件演化）
- ✅ 謙虛收尾（「互相幫忙」）

### 可優化的地方（P1 級別）

1. **關鍵字優化** — 「龍蝦」對外人不友善
   - 建議：「龍蝦（ClaudeCab，multi-agent Telegram bot 框架）」
   - 效果：+2 分（4→6）

2. **強化產業洞察** — 觀察有但沒有深化
   - 建議：「但真正的難度已經不在『怎麼串』，而是『怎麼管好一群會自己動的 agent』」
   - 效果：+2 分（6→8 附加價值，7→8 痛點）

3. **加入輕量 CTA** — 適合技術社群的互動
   - 建議：「如果你也在做 multi-agent 專案，歡迎交流你遇到最棘手的管理問題是什麼？」
   - 效果：+4 分（3→7）

**優化後預估：43/60**

### 優化版本

```
上禮拜在 @__i.change 和 @cyesuta.lee 的私域社群裡，看到他們在討論做 Agent 遇到的問題，就順手幫忙解答了一些關於龍蝦（ClaudeCab，一個 multi-agent Telegram bot 框架）的技術問題。

聊的內容大概是：架構怎麼設計、多 agent 管理的難度、event bus 怎麼協調、memory system 怎麼處理衝突，還有一些實作上的眉角。因為自己踩過很多坑，就整理了一些筆記給他們參考，算是互相幫忙吧。

有趣的是，從去年到現在 Agent 的這類管理需求與問題還是沒什麼太大的變化，門檻其實逐漸降低，Agent 套件也是越來越多，以往還要手搓對話，現在套件都幫你處理完了，串個接口的事情而已。但真正的難度已經不在「怎麼串」，而是「怎麼管好一群會自己動的 agent」——這部分的學習曲線反而變陡了。

所以還是能幫就幫，大家就是互相幫忙。如果你也在做 multi-agent 專案，歡迎交流你遇到最棘手的管理問題是什麼？
```

### 為什麼這是好案例

**人設建立文不需要高分，但要做對方向**：
- ❌ 不是要你導流（CTA 3 分就夠）
- ❌ 不是要你推銷（不需要硬推技術）
- ✅ 是要展示特質（大方/專業/願意分享）
- ✅ 是要拉近關係（謙虛、平易近人）

這個案例示範了「目標不同，評分標準不同」的原則。

### 學到的教訓

**診斷前必須確認貼文目標**：
- 初次評估誤判為「技術推廣文」（導流/導購）
- 實際是「人設建立文」（展示個人特質）
- 相同內容，目標不同，優化方向完全不同
- **印證了 framework.md 步驟 1：必須先理解目標**
