# SDK 0.2.76 → 0.2.119 Code Adjustment Plan (Batched Rollout)

**總體策略**：分批上線，每批獨立 commit、獨立驗證、可獨立 rollback。

| Batch | 內容 | 狀態 | Rollback 成本 |
|-------|------|------|--------------|
| 1 | SDK 升級 + Patch 重寫 | ✅ 完成（commit `a08adc8`） | `git revert` + `npm install`，約 2 分鐘 |
| 2 | 啟用 `includeHookEvents` + 新 message type handlers | ✅ 完成（`b7de4d0` + `4019520` 補第 3 個 patch） | revert sessionOptions 改動 |
| 2.1 | Callback hook 入口 `logger.info`（SDK 設計上 programmatic callback 不發 hook stream event） | ✅ 完成（本次） | revert callback 新增 log 行 |
| 3 | 啟用 `agentProgressSummaries` + task_progress summary 提取 + SubAgentMessageManager 優先顯示 summary | ✅ 完成（本次，含第 4 個 patch 需求——合併進 `cq-forwarded-flags`） | revert sessionOptions 改動 |
| 4 | `getContextUsage()` 接入 heartbeat | 🔓 **Viable**（本次 spike 證實 `session.query.getContextUsage()` 在 cQ 可用） | revert HeartbeatService 改動 |
| 5 (可選) | `startup()` pre-warm | 未做 | revert AppBootstrap |
| 6 (可選) | Discord `/subagents` 指令（用 `listSubagents`） | 未做 | 砍指令即可 |

### 實際執行與原計畫的差異

1. **Patches 從 2 個變成 3 個**：原計畫預期 0.2.110 修掉 settingSources + cwd 後只剩 thinking/extraArgs 與 F9 兩個 patch。實際發現 cQ 還漏傳 `includeHookEvents`、`includePartialMessages`、`agentProgressSummaries` 到 D9——同 0.2.110 那批 bug 的同類遺漏。追加 `cq-forwarded-flags` patch 統一修掉。
2. **SDK callback hook 不發 stream event**：`--include-hook-events` flag 只對 CLI-registered（settings.json / plugin）hooks 有效。我們的 hooks 全是 SDK programmatic callback，所以 `hook_started/hook_response` 不會出現。改用 callback 入口 `logger.info` + `EventType.SDK_HOOK_CB_*` 取得等價可視化。
3. **Pipeline test 證明替代 task_progress parsing 是安全的**：原計畫擔心 summary 偶爾 undefined 需要 fallback；`SubAgentMessageManager` 的 merge/formatter 本來就用 `summary ?? description`，無須額外處理。

## Batch 2：啟用 `includeHookEvents`

**目標**：從 pino log 看到 UserPromptSubmit/Stop hook 真的有跑（Phase 0 品質審查、Phase 1 記憶反思）。

### 改動點

`src/core/SDKSessionManager.ts` 建 sessionOptions 的區塊（約 line 395–430 附近），加：

```ts
sessionOptions.includeHookEvents = true;
```

### 零額外 code 需要

Line 1062–1065 已有：
```ts
if (systemMsg.subtype === 'hook_started') {
  logger.info({ sessionId, hookEvent: systemMsg.hook_event, hookName: systemMsg.hook_name }, 'V2 hook started');
} else if (systemMsg.subtype === 'hook_response') {
  logger.info({ ... outcome, exitCode, stderr }, 'V2 hook response');
}
```

→ 開 flag 後就會 log 出來。

### 驗證項目

| 項目 | 方法 | 成功標準 |
|------|------|---------|
| UserPromptSubmit 有跑 | 送訊息，grep log | `"V2 hook started"` + `hookEvent: "UserPromptSubmit"` 至少 1 次 |
| Stop hook Phase 0 有跑 | agent 回完後，grep log | `"V2 hook response"` + `outcome` 含 PASS/FAIL 字樣 |
| Stop hook Phase 1 有跑 | 同上 | 第二次 hook_response 或 hook_progress，或看 `agents/*/memory/` 是否有 timestamp 更新 |

### 風險

- `includeHookEvents` 讓 stream 多很多 event，可能影響 throughput（0.2.89 changelog 沒提到 overhead，但保險起見先在 dev 環境跑一輪）
- 若 hook 真的沒跑，這批會暴露真實 bug，比現在的「無法驗證」狀態好

### Rollback

改一行：`sessionOptions.includeHookEvents = false`（或刪掉）。或用 env var `HOOKS_DEBUG=true` 做 feature flag。

**目標**：sub-agent 進度有 AI-generated 摘要，Discord 使用者看得懂進度。

### 改動點

1. `src/core/SDKSessionManager.ts` sessionOptions 加：


2. `src/core/SDKSessionManager.ts` 裡 `extractSystemTaskText` 的 `task_progress` 分支（約 line 211–222），加讀取 `m.summary`：
   ```ts
   if (m.subtype === 'task_progress') {
     const event: SubAgentEvent = {
       // ...existing fields...
       summary: m.summary,  // 0.2.72+ 才有，可能是 undefined
     };
     return event;
   }
   ```

3. `src/core/SubAgentMessageManager.ts` 的 progress 格式化（line 50），用 summary 覆蓋 description：

- **替代性改動**：原本 task_progress 用 tool name 作為進度線索，新版改看 summary 文字。若 SDK 有時不送 summary，fallback 要穩（`r.summary ?? r.description`）。

### 驗證項目

| 項目 | 方法 | 成功標準 |

### Rollback

## Batch 4：`getContextUsage()` 接入 heartbeat

**目標**：heartbeat 帶 context window 使用率，提早警告爆窗。

### 改動點

**前提**：確認 `getContextUsage()` 能在 V2 persistent session 上呼叫（changelog 說是 control method，需要實測是否支援 cQ session）。

1. `src/services/HeartbeatService.ts` 或新增 helper：
   - 擴充 `CacheStatsProvider` 型別回傳值加 `context_usage_pct`
   - 在 provider 實作（應該在 SessionManager 那側）呼叫 active session 的 getContextUsage

2. AppBootstrap 將 contextUsage 併入 cache stats provider 注入到 HeartbeatService。

### 驗證項目

| 項目 | 方法 | 成功標準 |
|------|------|---------|
| heartbeat 有 context_usage | grep log | `cache.context_usage_pct` 欄位存在且 0–100 |
| 爆窗前能警告 | 故意塞長 context | context_usage_pct 接近 100 時有 warn log（需加 threshold） |

### 風險

- getContextUsage 可能只支援 `query()` 而非 `cQ` V2 session → 這批要先 spike 驗證，失敗就跳過不做。

### Rollback

- revert HeartbeatService 改動
- revert provider 注入

## Batch 5（可選）：`startup()` pre-warm

**目標**：首次 query 從 spawn + init 約 2–3 秒降到 ~100ms。

### 改動點

**前提**：`startup()` 是 `query()`-level API，未必能 pre-warm V2 persistent session。需要先看 0.2.119 的 API surface：
- 若 `startup()` 返回的是一個 warm 狀態，V2 createSession 能消耗這個狀態 → 可做
- 若是獨立的 cold-start 處理，只對 one-shot query 有用 → 只能在 SDKQueryManager（`initiative/social evaluator`）這種場景用

### 驗證項目

- 首次 query 從 log 的 `session.created` → 第一個 `V2 stream message received` 的 elapsed 顯著下降

### 風險

- 未必適用於 V2 persistent session。先做 spike，若無效就跳。
