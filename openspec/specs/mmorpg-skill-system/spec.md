## Purpose

此規格定義 ClaudeCab bot 管理系統的 MMORPG 啟發式遊戲化機制。本系統將經典 RPG 機制（裝備、熟練度、職業原型、角色面板、技能合成與成長循環）映射至 AI bot 的配置與成長，讓 bot 的管理體驗更像角色養成，而非軟體維護。核心設計哲學為「成長型差異化」：bot 透過累積的互動歷史發展出獨特能力，而非安裝預製通用技能。

## Requirements

### Requirement: 裝備系統

每個 bot 應（SHALL）維護一組結構化的能力槽位，定義其當前的主動配置。槽位系統必須（MUST）對同時裝備的工具數量設置上限，以防止情境過載並強制有意識地進行專業化選擇。

**槽位分類：**

- **人格槽（Persona Slot）**（1 個，固定）：身份與靈魂定義
- **協議槽（Protocol Slot）**（1 個，固定）：行為規則與運作限制
- **工具槽（Tool Slots）**（N 個，有上限）：提供外部能力的 MCP server
- **知識槽（Knowledge Slots）**（M 個，有上限）：提供專業知識的領域技能
- **記憶（Memory）**（固定，不可移除）：USER.md、MEMORY.md、每日日誌

系統必須（MUST）說明「移除工具往往能提升效能」的原則（情境清晰原則），且介面應（SHOULD）顯示當前槽位使用狀況，以鼓勵有意識地進行策展。

#### Scenario: 工具槽上限強制執行

- **WHEN** 使用者嘗試裝備超過已設定工具槽上限的 MCP server
- **THEN** 系統應（SHALL）拒絕此次新增，並顯示當前槽位使用量與上限值
- **AND** 系統應（SHALL）建議可替換的現有工具

#### Scenario: 套裝加成識別

- **WHEN** bot 擁有構成已定義「套裝」的 MCP server 與技能組合（例如：SEO 技能 + 社群策略技能 + browser MCP）
- **THEN** 角色面板應（SHALL）顯示生效的套裝名稱及其對應的加成描述

#### Scenario: 記憶槽不可移除

- **WHEN** 使用者嘗試卸載或刪除 USER.md、MEMORY.md 或記憶日誌檔案
- **THEN** 系統應（SHALL）拒絕此操作，並說明記憶是 bot 的永久組成部分

### Requirement: 熟練度系統

每個技能必須（MUST）依據累積使用次數追蹤五級熟練度評級。評級應（SHALL）在使用次數跨越門檻時自動晉升，並在技能長期不使用時應（SHALL）衰退。

**熟練度等級：**

| 等級 | 星級    | 稱謂       | 使用次數門檻 |
|------|---------|------------|--------------|
| 1    | ★☆☆☆☆  | Novice     | 0 次         |
| 2    | ★★☆☆☆  | Apprentice | 10 次        |
| 3    | ★★★☆☆  | Adept      | 50 次        |
| 4    | ★★★★☆  | Expert     | 200 次       |
| 5    | ★★★★★  | Master     | 500 次       |

熟練度資料應（SHALL）以人類可讀的 markdown 檔案形式儲存於技能目錄中（`references/proficiency.md` 或同等路徑）。不得（MUST NOT）要求已編譯的二進位狀態檔案。

#### Scenario: 熟練度在跨越門檻時晉升

- **WHEN** 技能的已記錄使用次數達到下一等級的門檻
- **THEN** 系統應（SHALL）將該技能的熟練度等級更新至下一級
- **AND** 角色面板應（SHALL）在下次渲染時反映新等級

#### Scenario: 熟練度因不使用而衰退

- **WHEN** 一個技能在可設定的衰退期間（預設：30 天）內未被使用
- **AND** 該技能當前處於 Adept 等級或以上
- **THEN** 系統應（SHALL）將熟練度等級降低一級
- **AND** 應（SHALL）在該技能的熟練度日誌中寫入衰退事件記錄

#### Scenario: 新技能從 Novice 起步

- **WHEN** 一個技能首次被建立或安裝
- **THEN** 其熟練度等級應（SHALL）初始化為 Novice（★☆☆☆☆）
- **AND** 其使用次數應（SHALL）設定為零

#### Scenario: Master 技能標記為可匯出

- **WHEN** 一個技能達到 Master 等級（★★★★★）
- **THEN** 系統應（SHALL）將該技能標記為可匯出
- **AND** 角色面板應（SHALL）為該技能顯示匯出操作入口

### Requirement: 職業原型系統

每個 bot 必須（MUST）在建立時被指定唯一一個職業原型。原型定義 bot 在多 bot 群組中的角色，並決定新手引導過程中預設推薦的技能與 MCP 組合。原型不得（SHALL NOT）限制 bot 日後可裝備的技能，但應（SHALL）影響系統提示詞與協議預設值。

**已定義的原型：**

- **Coordinator（協調者）** — 任務分解、品質監督、進度追蹤；對應 Tank 角色
- **Specialist（專精者）** — 深度領域執行、高品質產出、快速迭代；對應 DPS 角色
- **Support（輔助者）** — 資訊整理、排程、情境維護；對應 Healer 角色

系統必須（MUST）為每個原型提供預建的引導範本，在 bot 建立時設定最小可運作的人格與協議。

#### Scenario: 建立 bot 時選擇原型

- **WHEN** 使用者建立新 bot 並選擇一個原型
- **THEN** 系統應（SHALL）套用該原型的預設人格技能與協議配置
- **AND** 應（SHALL）在角色面板上顯示原型標籤

#### Scenario: 顯示群組組成建議

- **WHEN** 一個多 bot 群組中沒有任何 bot 具備 Coordinator 原型
- **THEN** 系統應（SHALL）顯示建議訊息，推薦加入一個 Coordinator

#### Scenario: 基於原型的技能推薦

- **WHEN** 使用者為 Specialist bot 瀏覽技能市集或合成建議
- **THEN** 系統應（SHALL）排序並篩選建議，優先呈現與 Specialist 原型相關的深度領域技能，而非通用技能

### Requirement: 角色面板

每個 bot 必須（MUST）提供一個角色面板，將其當前狀態匯總為單一可讀視圖。在第一階段，面板應（SHALL）僅從現有持久化資料（session DB、conversation DB、markdown 檔案、目錄掃描）衍生資料，不需要超出現有基礎設施的新追蹤機制。

**面板區塊：**

- **身份區塊**：bot 名稱、原型、模型、活躍天數
- **能力評分**：記憶深度（token 數 + 模式數）、USER.md 完整度
- **技能熟練度列表**：每個已裝備技能及其星級評分與等級標籤
- **裝備摘要**：已啟用的 MCP server 數量與知識技能數量
- **成就**：已解鎖的里程碑徽章及解鎖日期
- **統計數據**：總對話次數、每月 token 使用量、最常用技能

需要新追蹤機制的項目（技能熟練度、成就解鎖事件）在第一階段應（SHALL）顯示為「待追蹤」佔位符，並在第二階段追蹤機制實作後填充實際資料。

#### Scenario: 面板從現有資料來源渲染

- **WHEN** 使用者開啟 bot 的角色面板
- **THEN** 系統應（SHALL）在 2 秒內使用現有資料填充所有第一階段欄位（活躍天數、對話次數、token 使用量、記憶檔案大小、技能目錄列表、MCP 數量）
- **AND** 需要第二階段追蹤的欄位應（SHALL）顯示「尚未追蹤」佔位符

#### Scenario: 從檔案計算記憶深度

- **WHEN** 面板渲染記憶深度評分
- **THEN** 系統應（SHALL）估算 MEMORY.md 的 token 數量、`memory/` 中每日日誌檔案的數量，以及 MEMORY.md 中已識別模式的數量
- **AND** 應（SHALL）以複合進度條和原始數據的形式呈現這些資訊

#### Scenario: 每次對話後面板更新

- **WHEN** 與 bot 的對話階段結束
- **THEN** 角色面板資料應（SHALL）在下次載入面板時反映新的對話次數與 token 使用量，無需手動刷新

### Requirement: 技能合成系統

系統應（SHALL）支援一套結構化的工作流程，用於從 bot 累積的經驗中提煉可重用技能。工作流程必須（MUST）經過四個階段：素材收集、模式發掘、草稿撰寫與品質評級。任何階段都不得（SHALL NOT）需要已編譯的應用程式邏輯——bot agent 本身使用其現有的讀寫能力協調整個工作流程。

**階段定義：**

1. **素材收集**（自動）：每日日誌條目、MEMORY.md 模式、USER.md 偏好，以及正向／負向互動訊號被動累積。
2. **模式發掘**（半自動）：當某個行為模式在 MEMORY.md 中出現 5 次或以上時，系統或 bot 應（SHALL）向使用者呈現合成建議。
3. **草稿撰寫**（agent 輔助，使用者確認）：bot 依照 agentskill-expertise 設計原則生成候選技能；使用者在安裝前進行審閱與核准。
4. **品質評級**（持續）：合成的技能隨著使用證據的累積，在四級量表上進行評級。

**品質等級：**

| 等級       | 顏色   | 標準                                               |
|------------|--------|----------------------------------------------------|
| Draft      | 綠色   | 剛提煉出來，尚未驗證                               |
| Refined    | 藍色   | 20+ 次使用，穩定且有效                             |
| Masterwork | 紫色   | 可匯出至其他 bot 或使用者                          |
| Legendary  | 橘色   | 社群驗證、高品質、廣泛適用                         |

#### Scenario: 重複模式觸發合成建議

- **WHEN** MEMORY.md 中出現某個獨特行為模式達五次或以上
- **THEN** bot 應（SHALL）在下次使用者互動時提出合成建議，說明所觀察到的模式並提議將其提煉為一個具名技能

#### Scenario: 使用者確認後 bot 起草技能

- **WHEN** 使用者確認合成建議
- **THEN** bot 應（SHALL）在 `.claude/skills/` 下生成一個完整的技能目錄，至少包含含有觸發條件、核心原則的 SKILL.md，以及至少一份良好範例文件的 `references/` 子目錄
- **AND** 新技能應（SHALL）以 Draft 等級與 Novice 熟練度初始化

#### Scenario: 技能等級晉升至 Refined

- **WHEN** 一個合成技能達到 20 次已記錄使用
- **THEN** 其品質等級應（SHALL）自動從 Draft 晉升至 Refined
- **AND** 角色面板應（SHALL）在下次渲染時更新等級徽章

#### Scenario: Masterwork 技能可匯出

- **WHEN** 一個技能達到 Masterwork 等級
- **THEN** 系統應（SHALL）提供匯出功能，將技能目錄打包為可攜帶的壓縮檔
- **AND** 壓縮檔必須（MUST）包含技能的 `references/` 內容與熟練度日誌

### Requirement: 成長循環

系統應（SHALL）定義三個巢狀時間週期循環（每日、每週、每月），提供短期、中期與長期的參與錨點。每個週期應（SHALL）產生具體可見的產出，使進度對使用者保持可感知。

**週期定義：**

- **每日** — 晨間簡報（昨日回顧 + 今日計畫）、即時任務執行、每次對話後的記憶回寫。
- **每週** — bot 主動發起的週回顧，總結關鍵互動，對 MEMORY.md 進行模式提煉，更新頻繁使用技能的技能範例庫。
- **每月** — 含面板快照差異的成長報告（活躍天數變化、等級變化、新成就），技能成熟度晉升檢查（符合等級晉升資格的技能），基於每月模式累積的新技能發掘建議。

系統不得（SHALL NOT）要求使用者手動觸發任何週期產出。排程 agent 或 Stop Hook 回調應（SHALL）自動驅動每個週期。

#### Scenario: 對話結束後每日記憶回寫

- **WHEN** 一個對話階段結束
- **THEN** bot 應（SHALL）在 `memory/` 中當天的日誌檔案追加一條摘要條目
- **AND** 應（SHALL）以本次對話中識別到的任何新模式或強化模式更新 MEMORY.md

#### Scenario: 週循環觸發模式提煉

- **WHEN** 週循環觸發（可設定的日期，預設為週日）
- **THEN** bot 應（SHALL）產生一份週回顧文件，總結前三大互動主題
- **AND** 應（SHALL）識別任何已跨越合成建議門檻（≥5 次出現）的模式

#### Scenario: 月報告含面板差異

- **WHEN** 月循環觸發（每月第一天）
- **THEN** bot 應（SHALL）生成包含角色面板關鍵指標前後對比的每月成長報告（活躍天數、技能等級變化、新解鎖成就）
- **AND** 應（SHALL）將報告儲存於 `memory/monthly/YYYY-MM.md`

### Requirement: OpenClaw 差異化契約

ClaudeCab 的遊戲化設計應（SHALL）明確區別於安裝型技能市集（以 OpenClaw 為代表），在來源、獨特性、切換成本與品質契合度等維度上加以區分。這些差異化特性是規範性設計約束，而非單純的行銷定位——每個功能決策必須（MUST）依此進行評估。

**差異化維度：**

| 維度           | 安裝型（OpenClaw 模式）        | 成長型（ClaudeCab 模式）                |
|----------------|--------------------------------|-----------------------------------------|
| 技能來源       | 從市集下載                     | 從個人互動中提煉                        |
| 獨特性         | 低（與所有使用者共享）         | 高（獨特於擁有者的使用歷史）            |
| 情感投入       | 低（安裝後即忘）               | 高（擁有者親手培育）                    |
| 切換成本       | 低（技能通用）                 | 極高（記憶 + 演化 + 情感連結）          |
| 品質契合度     | 通用（可能不適合使用者）       | 量身定制（從使用者自身資料中成長）      |
| 成長可見性     | 無                             | 角色面板 + 成就系統                     |

系統應（SHALL）強制執行技能上限（裝備系統），以防止累積數百個通用技能的反模式，因為此模式會透過情境混亂降低 agent 效能。

系統應（SHALL）使成長可見（角色面板），讓使用者感知其投資隨時間累積，透過「贏得的獨特性」而非功能廣度創造留存黏性。

#### Scenario: 技能上限防止情境過載

- **WHEN** bot 已裝備的技能與 MCP 工具總數將超過已設定的上限
- **THEN** 系統應（SHALL）阻止此次新增
- **AND** 應（SHALL）顯示說明訊息，解釋超過上限會有情境混亂的風險，並引用「更少、更契合的工具優於大量通用組合」的設計原則

#### Scenario: 向使用者呈現贏得的獨特性

- **WHEN** 一個 bot 已累積 90 天活躍使用，且至少有一個技能達到 Adept 等級或以上
- **THEN** 角色面板應（SHALL）顯示「贏得的獨特性」指標，展示 bot 的個人化深度（例如：模式數量、已合成技能數、互動歷史深度），強調此配置無法透過安裝市集技能來複製

#### Scenario: 匯出時保留成長資產

- **WHEN** 使用者匯出一個 Masterwork 或 Legendary 技能
- **THEN** 匯出包必須（MUST）包含所有 `references/` 文件、熟練度日誌與技能成長過程中累積的使用統計資料，使接收方 bot 能繼承完整的知識資產，而非僅是一個空白範本
