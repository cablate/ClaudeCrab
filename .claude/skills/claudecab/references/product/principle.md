# ClaudeCab 功能開發原則

> 開發新功能前，用這些問題檢驗是否符合產品定位。

---

## ✅ 應該做的

1. **強化代理隔離** - 讓每個 Agent 更獨立、更專業
2. **改善通訊體驗** - Telegram 互動更流暢
3. **擴展記憶系統** - 更好的學習與回憶機制
4. **支援排程任務** - Cron、事件驅動
5. **簡化部署** - 一鍵安裝、一鍵啟動
6. **讓角色活起來** - 每個 Agent 要有可見的生命感（吐槽、心情、嘀咕）
7. **事件驅動展示** - 所有行為變成結構化事件，前端可渲染

---

## ❌ 不應該做的

1. **重造輪子** - 已有好工具的領域用 MCP 整合
2. **追求全能** - 不是每個功能都要自己實作
3. **複雜化部署** - 不引入過多依賴
4. **偏離核心** - 不做與「代理管理」無關的功能

---

## 🤔 功能評估清單

當考慮新功能時，問自己：

| 問題 | 期望答案 |
|------|----------|
| 這是否強化「目錄即代理」的核心概念？ | ✅ Yes |
| 這是否改善使用者透過 Telegram 操控 Agent 的體驗？ | ✅ Yes |
| 這能否透過 MCP 整合而非自己實作？ | 優先用 MCP |
| 這是否保持部署的簡單性？ | ✅ Yes |
| **Demo Day 加速判斷：使用者能在展示中感受到嗎？** | **能 → 做，不能 → 延後** |

---

## 設計原則

### 展示優先（v2.0 核心原則）

**可見的生命感 > 看不見的引擎正確性。**

- 使用者感受到的是 bot 的反應、情緒、吐槽——不是你的 cascade protection
- 每個 bot 行為都應該產出結構化事件，讓前端能渲染
- Telegram 是事件的消費者之一，不是唯一出口
- 引擎功能暫時凍結，優先讓角色的人格可被看見

判斷標準：**「使用者在 demo 中能感受到嗎？」** 能 → 做。不能 → 延後。

### SDK 優先

充分利用 Claude Agent SDK 內建功能，避免重複造輪子：
- Skills 機制 → 用於協議和人格模組化
- MCP 支援 → 用於外部工具整合
- Resume 機制 → 用於對話連續性

### Agent 自主管理

記憶、人格等進階功能完全由 Agent 透過 CLAUDE.md 指令自行操作：
- 引擎層（`src/`）零感知
- 不建立「組裝層」注入記憶內容到 systemPrompt
- SDKQueryManager 可獨立抽離到其他專案

### 配置驅動

透過 JSON/YAML 配置 Agent，降低使用門檻：
- `agent.json` - ClaudeCab 元資料
- `settings.local.json` - 權限配置
- `schedules/*.yaml` - 排程定義
